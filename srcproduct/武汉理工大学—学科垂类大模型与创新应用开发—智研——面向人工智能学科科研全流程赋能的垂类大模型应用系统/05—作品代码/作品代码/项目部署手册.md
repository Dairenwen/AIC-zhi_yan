# “智研”科研智能助手 Web 系统部署手册

> **适用目录**：`Web code/zhiyan_sub`\
> **文档用途**：项目提交材料、部署交接和运维参考\
> **编写日期**：2026-09-14\
> **应用标识**：Zhiyan Research Assistant；根目录 README 标注为 Demo V1.2

## 1. 项目概述

“智研”是面向科研人员的前后端分离 Web 系统。前端使用 Vue 3、TypeScript 和 Vite，后端使用 Flask、SQLAlchemy 和 PostgreSQL；系统将文献检索、论文精读、创新点生成、学术合规、学术翻译、专利撰写、科研绘图、学术速递、个人知识库和科研工具统一到一个工作台中。

系统的核心请求链路如下：

```text
浏览器
  │ HTTPS
  ▼
Nginx/Apache（静态文件、/api 反向代理、上传限制）
  ├── frontend/dist              Vue 单页应用
  └── backend:5000               Flask WSGI
        ├── PostgreSQL 16        主系统 zhiyan schema
        ├── 内嵌知识库运行时       knowledge_base schema（默认）
        ├── Agent 子进程          论文精读、专利、绘图、翻译等
        └── 外部模型服务          OpenAI 兼容接口 / Ollama（按需）

可选基础设施：Redis、Milvus Lite、Elasticsearch、GPU/CUDA、短信服务商。
```

默认情况下，知识库服务由 Flask 进程启动在本机随机端口，不需要单独暴露 `8768`；只有将 `KNOWLEDGE_BASE_EMBEDDED=false` 时才需要部署独立知识库服务。

## 2. 部署方式与边界

### 2.1 本地演示部署

适用于 Windows 10/11、项目验收和功能演示。前端使用 Vite 开发服务器，后端使用 Flask 开发服务器，PostgreSQL/Redis 由 Docker Compose 启动。

### 2.2 生产部署

推荐 Linux + Nginx + Gunicorn + PostgreSQL。前端先构建为静态文件，后端以 WSGI 服务运行；Flask 的 `--debug` 仅用于开发，不得用于公网生产。

### 2.3 Docker Compose 的职责

根目录 `docker-compose.yml` 目前只定义：

- `postgres`：PostgreSQL 16，映射到 `127.0.0.1:5432`；
- `redis`：Redis 7 Alpine，映射到 `127.0.0.1:6379`。

Compose **不构建前端和 Flask 镜像**，也不会自动安装 Agent 运行时。数据库、后端和前端仍按本手册分别部署。

> **数据库交付检查**：Compose 文件挂载了 `database_exports/zhiyan_full_20260814.sql`，但当前 `zhiyan_v1.0` 目录未包含该文件。正式交付包必须补入经确认的数据库导出文件，或在首次初始化空数据库时删除该挂载并使用组织提供的 schema 初始化脚本；否则 PostgreSQL 容器可能因找不到绑定文件而启动失败。项目代码不会在 Flask 启动时自动创建全部基础表。

### 5.3 常用配置分组

| 分组    | 主要变量                                                                  | 默认/建议                             |
| ----- | --------------------------------------------------------------------- | --------------------------------- |
| 鉴权    | `SECRET_KEY`、`AUTH_TOKEN_MAX_AGE`、`AUTH_COOKIE_SECURE`                | 生产必须使用强随机密钥和 HTTPS                |
| 数据库   | `DATABASE_URL`                                                        | `postgresql+psycopg://.../zhiyan` |
| 跨域    | `CORS_ORIGINS`                                                        | 只填写实际前端域名，逗号分隔                    |
| 平台模型  | `QWEN_DPO_BASE_URL`、`QWEN_DPO_MODEL`、`QWEN_DPO_API_KEY`               | 使用供应商原生模型 ID；不要把 Key 写入代码         |
| 模型校验  | `MODEL_VERIFY_TIMEOUT_SECONDS`、`MODEL_HTTP_MAX_RETRIES`               | 默认 60 秒、3 次重试                     |
| 上传    | `PAPER_UPLOAD_MAX_BYTES` 等 `*_UPLOAD_MAX_BYTES`                       | 默认论文及 Agent 附件 50 MB              |
| 知识库   | `KNOWLEDGE_BASE_EMBEDDED`、`KB_*`、`ELASTICSEARCH_ENABLED`              | 默认内嵌；Milvus/ES 默认关闭               |
| Agent | `*_RUNTIME_ROOT`、`*_TIMEOUT_SECONDS`                                  | 路径相对 `backend` 解析，保持目录随项目交付       |
| 降级策略  | `MANUSCRIPT_ALLOW_DETERMINISTIC_FALLBACK`、`PATENT_DRAFTING_FAKE_MODE` | 生产关闭伪造/Fixture 模式，确定性底稿须在界面标识     |

## 7. 数据库初始化与数据迁移

### 7.1 基础 schema

先恢复正式交付包提供的基础数据库导出，确保 `zhiyan` 和 `knowledge_base` schema 及核心表存在。恢复示例：

```bash

```

恢复前应确认导出文件来源、版本和是否包含用户数据；生产恢复前先备份现有数据库。当前代码目录没有根级 Alembic 基础迁移目录，因此不能仅依赖 `flask db upgrade` 从空库推导完整业务 schema。

### 11.2 Linux 生产启动（Gunicorn）

Gunicorn 不在 `backend/requirements.txt` 中，生产环境额外安装：

```bash
cd /opt/zhiyan/backend
source .venv/bin/activate
pip install gunicorn
gunicorn --bind 127.0.0.1:5000 --workers 1 --threads 8 \
  --timeout 3600 --access-logfile - --error-logfile - wsgi:app
```

默认使用 1 个 Worker 是因为内嵌知识库和部分 Agent 状态位于 Flask 进程内；扩展到多 Worker 前，应将知识库改为独立服务并验证 SSE、任务状态和上传目录的一致性。

可选 systemd 单元 `/etc/systemd/system/zhiyan.service`：

```ini
[Unit]
Description=Zhiyan Flask API
After=network.target postgresql.service

[Service]
User=zhiyan
Group=zhiyan
WorkingDirectory=/opt/zhiyan/backend
EnvironmentFile=/opt/zhiyan/backend/.env
ExecStart=/opt/zhiyan/backend/.venv/bin/gunicorn --bind 127.0.0.1:5000 --workers 1 --threads 8 --timeout 3600 wsgi:app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

启用：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now zhiyan
sudo systemctl status zhiyan
sudo journalctl -u zhiyan -f
```

## 12. Nginx 反向代理示例

```nginx
server {
    listen 80;
    server_name research.example.edu;
    root /opt/zhiyan/frontend/dist;
    client_max_body_size 50m;

    location /api/ {
        proxy_pass http://127.0.0.1:5000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

申请 HTTPS 证书后，将 `listen 80` 重定向到 HTTPS，并保持后端 `AUTH_COOKIE_SECURE=true`。`proxy_buffering off` 和较长的读取超时用于保证任务 SSE 进度流不被代理缓存或提前断开。

## 13. 部署后验收

### 13.1 健康检查

```bash
curl -fsS http://127.0.0.1:5000/api/v1/health/live
curl -fsS http://127.0.0.1:5000/api/v1/health/ready
```

预期：`live` 返回 `status=up`；`ready` 返回数据库和各 Agent 状态。`ready` 为 `degraded` 不一定表示 API 进程故障，常见原因是可选模型、`uv`、Milvus 或外部服务尚未配置，应根据返回的 `agents` 逐项处理。

### 13.2 前端和鉴权

1. 浏览器访问前端域名，确认首页、路由刷新和静态资源均返回 200。
2. 使用正式账号登录，确认 `GET /api/v1/auth/me` 返回当前用户。
3. 普通用户不能看到或访问管理员知识库界面；管理员可访问知识库管理入口。
4. 创建一条科研任务，确认任务详情和 SSE 进度可持续刷新。
5. 上传一份小型 PDF，确认上传限制、任务归属和下载结果正常。

PowerShell 健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:5000/api/v1/health/live
Invoke-RestMethod http://127.0.0.1:5000/api/v1/health/ready
```

### 13.3 自动化检查

```bash
cd /opt/zhiyan/backend
```

## 15. 知识库、向量和模型服务注意事项

1. `KNOWLEDGE_BASE_EMBEDDED=true` 时，内嵌服务会复用 `DATABASE_URL`，并将知识库表放在 `knowledge_base` schema；主系统表位于 `zhiyan` schema。
2. `KB_MILVUS_ENABLED=1` 时，`KB_MILVUS_URI` 必须是部署机可访问的路径。Windows 示例中的 `E:/kb_pdf_store/...` 不能直接复制到 Linux；Linux 应使用 `/var/lib/zhiyan/milvus_lite.db` 等本机路径。
3. 更换 Embedding 模型或向量维度后，必须重建 Milvus collection/index，并同步 `KB_MILVUS_DIM`；不能仅修改 `.env`。
4. 个人 RAG 返回 `NO_EVIDENCE` 或 `AUTHORIZED_LIBRARY_EMPTY` 时，先检查用户是否拥有文件夹、文档是否已解析出 `paper_chunks`、集合授权关系是否存在，再判断模型服务。
5. 平台模型 `/v1/models` 或聊天接口返回 502/超时时，应分别检查 DNS、TLS、代理端口、模型名和 API Key；健康检查成功不代表外部模型可用。

## 16. 备份、升级与回滚

### 16.1 备份

```bash
mkdir -p /var/backups/zhiyan
pg_dump 'postgresql://zhiyan:<密码>@127.0.0.1:5432/zhiyan' \
  | gzip > /var/backups/zhiyan/zhiyan_$(date +%Y%m%d_%H%M%S).sql.gz
tar -czf /var/backups/zhiyan/files_$(date +%Y%m%d_%H%M%S).tgz \
  backend/uploads backend/generated backend/knowledge_base_runtime/infrastructure/file-storage/data
```

备份范围包括 PostgreSQL、用户上传文件、Agent 产物、知识库文件和 Milvus 文件（如启用）。备份中可能包含论文和个人数据，必须加密并限制访问。

### 16.2 升级顺序

1. 备份数据库和文件目录。
2. 停止旧 Flask 服务，保留旧版本目录。
3. 部署新代码并核对 `backend/.env`。
4. 安装新增依赖，执行幂等初始化/迁移命令。
5. 运行健康检查、后端测试和前端构建。
6. 启动新服务，观察日志和关键业务流程。
7. 验收通过后再清理旧版本；失败时恢复旧代码、旧依赖和数据库备份。

## 17. 常见故障排查

| 现象                                            | 可能原因                                           | 处理方法                                                     |
| --------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| Compose 报绑定文件不存在                              | 缺少 `database_exports/zhiyan_full_20260814.sql` | 补齐正式导出，或按“数据库交付检查”处理挂载                                   |
| `/health/live` 正常但 `/health/ready` 为 degraded | Agent/数据库/模型等组件未就绪                             | 查看 `components` 和 `agents` 字段，逐项核验                       |
| 登录 401/403                                    | 用户不存在、密码未初始化、Cookie/CORS/CSRF 配置错误             | 执行 `set-user-password`，检查同源访问、HTTPS 和 CSRF 请求头           |
| 模型库验证 15 秒超时                                  | 前端旧 Axios 超时或模型网关排队                            | 使用当前前端重新构建；检查 `MODEL_VERIFY_TIMEOUT_SECONDS` 和网关日志       |
| 上传后任务不推进                                      | Agent 子运行时、`uv`、模型或目录权限异常                      | 检查服务日志、`*_RUNTIME_ROOT`、缓存目录和超时设置                        |
| SSE 断流或只显示最终结果                                | Nginx 缓冲、读取超时或多 Worker 状态不一致                   | `proxy_buffering off`、提高 `proxy_read_timeout`，先用单 Worker |
| 个人 RAG 无引用                                    | 用户没有授权文档切片，或 Milvus/Embedding 未就绪              | 检查 `paper_chunks`、集合关系和知识库 readiness                     |
| 公式识别状态 unavailable                            | 专用 `.venv` 或模型权重缺失                             | 在 runtime 目录安装依赖，确认 `FORMULA_RECOGNITION_PYTHON` 指向专用解释器 |
| Linux 生成图表中文乱码                                | 未安装 CJK 字体                                     | 安装 Noto Sans CJK，并设置 `ACADEMIC_FIGURE_FONT_PATH`         |
| Windows 统一启动脚本失败                              | 脚本包含开发机 Node 绝对路径                              | 分别启动 Flask 和 Vite，或修改脚本中的 Node 路径                        |
| 测试找不到 `app`                                   | 测试工作目录不正确                                      | 进入 `backend` 后执行 `python -m pytest -q`                   |

## 18. 安全与合规要求

- 生产必须启用 HTTPS、`AUTH_COOKIE_SECURE=true`，并使用随机 `SECRET_KEY` 和 `MODEL_CONFIG_ENCRYPTION_KEY`。
- 数据库、Redis、Milvus 和内嵌知识库端口只允许内网访问，不直接暴露到公网。
- `CORS_ORIGINS` 不得使用任意来源；上传目录不得通过 Nginx 直接列目录或执行脚本。
- API Key、短信密钥、数据库密码不得写入 Git、截图、日志、Markdown 提交材料或前端源码。
- 普通用户只能访问自己的任务、历史、项目和知识库；系统管理员接口应通过角色权限和反向代理同时保护。
- 对论文、专利、个人知识库等上传数据执行访问控制、定期备份、生命周期清理和最小权限管理。
- `PATENT_DRAFTING_FAKE_MODE`、Fixture 回退和确定性降级只用于离线验收；正式结果必须明确标注模型不可用、外部检索失败或人工复核要求。

## 19. 部署完成判定

满足以下条件即可判定为“部署完成”：

1. PostgreSQL 可连接，基础 schema 和项目扩展表初始化成功。
2. Flask 服务稳定监听 `127.0.0.1:5000`，`/api/v1/health/live` 返回 200。
3. `/api/v1/health/ready` 的数据库为 `up`，可选依赖的降级原因已记录。
4. 前端 `dist` 已构建，Nginx/IIS 可加载首页且前端路由刷新不返回 404。
5. 正式账号登录、CSRF 写操作、任务创建、SSE 进度和至少一个文件上传流程通过。
6. 管理员与普通用户权限边界通过验证，日志、备份和服务自动重启策略已配置。
7. 所有外部模型、短信、Milvus、GPU 等未启用能力均在交接记录中明确标注，而不是默认为已验证。
